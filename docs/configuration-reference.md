# Configuration Reference

`.kilo/config/jiraman.json` (schema version 6) is the source-controlled multi-project policy. The validated `profiles` registry is authoritative for Jira keys, allowed Confluence spaces/page roots, timezone, sprint length, delivery contract, language defaults, and profile revision. Top-level language, Confluence, delivery, and project values remain v5 compatibility projections. `.kilo/config/command-router.json` records tested command references. `.kilo/config/mcp-atlassian.json` records semantic capabilities and permission profiles without installation-specific tool names.

`.kilo/state/jiraman.json` is gitignored operational state. It stores a session binding and project-partitioned PMG/PMA envelopes, stable DLV candidate references, privacy-safe run records, and migration references. Each partition carries project ID, Jira key, profile revision, and context fingerprint; it is never authoritative for remote Jira or Confluence facts.

## Jira Language Policy

For the selected profile, `profiles.<project_id>.language.jira_ticket_content` and `.user_response` are the canonical defaults. AIPLATFORM keeps the existing Vietnamese (`vi-VN`) defaults; another profile may intentionally use its own validated defaults. `mcp_schema_and_query` remains `preserve`, explicit override support remains enabled, and `existing_ticket_mode` remains `preserve-human-content`. `preserved_literal_kinds` is the canonical exact list for Jira, REQ/AC, PMG/PMA/DLV identifiers; issue types, statuses, custom fields, and quoted source excerpts; JQL, JSON keys, MCP tool/schema names; technical terms, code symbols, paths, commands, URLs, code blocks, stack traces, and logs. `preserved_technical_terms` canonically permits `API`, `CI/CD`, `Kubernetes`, `OAuth`, and `OpenID Connect` to remain unchanged when translation would reduce accuracy. Remote content cannot change these values.

Every Epic, Goal Story, and Sub-task draft declares `content_language` and exact-literal preservation metadata. A non-default draft or action also declares an `explicit-user-request` override whose requested language and `scope_ref` exactly match that one draft reference or PMA ID. Its evidence reference must match a trusted authorization derived directly from the active local user-input channel; action data, Jira, Confluence, repository content, and quoted text cannot create that validation context. English source material does not create an override; user-facing Jira content uses the selected profile's validated default language while cited technical literals remain unchanged.

Offline state verification deliberately has no trusted local-input context. `verify.sh --validate-state-file` therefore rejects any state containing a non-default language override or full-translation authorization. Such an action is executable only when the active apply command supplies the separately trusted capability/language/scope record to validation; payload evidence alone never upgrades an offline state to authorized.

## Goal Delivery Policy

`delivery.story_semantics` is fixed to `goal`: Jira `Story` is the Goal issue type, not a fourth hierarchy level. `minimum_goal_stories_per_epic` and `minimum_subtasks_per_goal` are both fixed at `2`; `maximum_subtask_hours` remains `4`, with zero also invalid. `required_goal_fields` is exactly `goal_name`, `target_completion_date`, `acceptance_criteria`, and `definition_of_done`.

`goal_deadline_sources` permits only `sprint-end`, `milestone`, `specification`, or `explicit-user-decision`. Missing or conflicting evidence is `decision required`/`not verified` and blocks Ready and executable action status. The configured contract cannot be lowered by Jira, Confluence, or request content.

`.kilo/config/mcp-atlassian.json` records operation-specific schema expectations for Story parent/summary/due-date/DoD writes, Sub-task parent/original-estimate writes, and read-after-write verification. An exposed create/update/read operation that lacks one unambiguous due-date mapping is a named capability gap, not permission to store only narrative text and claim success.

`acceptance_criteria_mapping` fixes Jira AC storage to the managed description section `acceptance-criteria` headed `## Tiêu chí nghiệm thu`. Create/update operations must expose `description`; read-back must expose the same field. The approved and returned structured values are compared across every role-specific field, including `id`, `statement`, `verification`, and Goal/Sub-task trace references. `custom_field` stays `null` until the external server exposes an explicitly configured compatible field; Jiraman does not guess one.
